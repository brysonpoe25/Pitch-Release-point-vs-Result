# Supabase schema & seed data

Two files, meant to be run in order against a fresh Supabase (Postgres)
project's SQL Editor:

1. **`schema.sql`** — tables (`games`, `pitchers`, `batters`, `pitches`),
   two summary views (`pitch_outcome_summary`, `pitcher_release_summary`),
   indexes, and Row Level Security policies (public read, no write access
   for anon/authenticated).
2. **`seed.sql`** — generated `insert` statements loading
   `data/pitch_data.csv` (315 pitches from a college baseball TrackMan
   export) into the schema above.

`seed.sql` is generated by [`../scripts/build_data.py`](../scripts/build_data.py)
from `../data/pitch_data.csv` — re-run that script after editing the CSV to
regenerate it (it also refreshes `../web/src/data/pitches.json`, the static
fallback the website uses when Supabase isn't configured).

```bash
python3 scripts/build_data.py
```

## Loading into a new project

1. Create a project at [supabase.com](https://supabase.com/).
2. **SQL Editor → New query**, paste `schema.sql`, run.
3. New query again, paste `seed.sql`, run.
4. Grab the project URL and anon key from **Project Settings → API** and
   set them as `NEXT_PUBLIC_SUPABASE_URL` / `NEXT_PUBLIC_SUPABASE_ANON_KEY`
   in `web/.env.local` (and in your Vercel project's Environment Variables
   for the deployed site) — see [`../web/README.md`](../web/README.md).

Both files are idempotent (`on conflict ... do nothing`), so re-running
them is safe.
